# Prompt: Reorganize EPIK8S Platform Architecture

## Objective

Reorganize the EPIK8S Helm charts and deployment architecture into a modular platform while **preserving 100% compatibility with the current deployments**.

This is **not** a redesign of EPIK8S. The goal is to improve maintainability, modularity, and future extensibility without changing the behavior of existing beamlines.

The resulting architecture must be capable of deploying a completely new Kubernetes cluster from scratch, while also being able to reproduce the current production deployments exactly.

---

## Non-Functional Requirements

### 1. Backward Compatibility (Highest Priority)

The current deployments of SPARC, BTF, ELI, and all existing facilities must continue to work without functional changes.

The generated Kubernetes resources should remain equivalent to the current deployment unless explicitly requested otherwise.

Do **not** introduce breaking changes.

Do **not** change existing IOC behavior.

Do **not** modify network behavior.

Do **not** modify service discovery.

Do **not** change PV addressing.

Existing values.yaml files should continue to work with minimal or no modifications.

---

### 2. Preserve Existing Deployment

The new organization must be able to reproduce:

* namespaces
* StatefulSets
* Deployments
* Services
* PVCs
* ConfigMaps
* Secrets
* NetworkAttachmentDefinitions
* LoadBalancer Services
* MCP servers
* IOC deployments

exactly as they are today.

---

### 3. Separate Platform Services from Beamline Services

Introduce a clear separation between:

Platform Infrastructure

* ArgoCD
* networking
* storage
* logging
* monitoring
* backup
* AI platform
* databases

and

Beamline Services

* IOCs
* EPICS services
* MCP server
* beamline-specific applications
* beamline configuration
* beamline-specific NetworkAttachmentDefinitions

---

## Desired Repository Organization

A possible target organization is:

```text
epik8s-platform/
    backend/
    networking/
    storage/
    logging/
    monitoring/
    backup/
    ai/

epik8s-beamline/
    sparc/
    btf/
    eli/
```

This structure is only a guideline.

A better organization is acceptable if it satisfies all compatibility requirements.

---

## Networking

Generalize networking into reusable components.

Examples include:

* MetalLB
* IPAddressPools
* L2Advertisements
* Multus
* CNI configuration
* reusable NetworkAttachmentDefinition templates
* ingress controllers

Beamlines should declare networking requirements rather than installing networking infrastructure.

Example concept:

```yaml
network:
    camera:
        enabled: true
        attachment: sparc-camera
```

instead of embedding networking implementation details inside the beamline chart.

---

## Storage

Generalize storage.

Platform responsibilities include:

* StorageClasses
* CSI configuration
* NFS provisioners
* Longhorn/Ceph configuration

Beamlines should simply request storage.

Example:

```yaml
storage:
    autosave:
        size: 5Gi
```

The platform should determine how this storage is provisioned.

---

## Logging

Create a centralized logging platform.

Platform responsibilities:

* Loki
* Grafana
* Grafana Alloy (preferred) or Promtail
* Event Exporter

Beamlines should automatically expose logs through labels such as:

* facility
* namespace
* IOC
* component

without requiring local logging infrastructure.

---

## Monitoring

Generalize monitoring.

Platform:

* Prometheus
* Alertmanager
* exporters

Beamlines should only expose metrics.

---

## Backup

Generalize backup infrastructure.

Platform:

* Velero
* CSI snapshots
* backup schedules

Beamlines should declare backup requirements instead of implementing backup logic.

---

## AI Platform

The AI platform should be independent from beamlines.

Examples:

* LibreChat
* Qdrant
* RAGFlow
* Local LLMs

However, every beamline should continue to deploy its own MCP server.

The MCP server remains part of the beamline because it represents the beamline knowledge and operational context.

---

## Beamline Responsibilities

Each beamline should remain self-contained.

A beamline owns:

* IOC deployments
* services
* MCP server
* beamline-specific configuration
* PV prefixes
* beamline-specific NetworkAttachmentDefinitions
* ConfigMaps
* Secrets

---

## Preserve Current Deployment Semantics

Current deployment semantics must remain unchanged.

The reorganization should only move responsibilities into more appropriate modules.

No functional changes should be introduced unless explicitly requested.

---

## Migration Strategy

The implementation should proceed incrementally.

Suggested phases:

1. Extract common infrastructure into reusable charts.
2. Keep existing beamline charts functional.
3. Introduce compatibility wrappers if necessary.
4. Validate that generated manifests remain equivalent.
5. Migrate one platform component at a time.

The migration should allow existing production systems to continue operating during the transition.

---

## Validation

For every proposed refactoring, verify that:

* Kubernetes manifests are functionally equivalent.
* Existing namespaces remain unchanged.
* Existing Service names remain unchanged.
* Existing PVC names remain unchanged.
* Existing LoadBalancer IP assignments remain unchanged.
* Existing NetworkAttachmentDefinitions remain unchanged.
* Existing MCP endpoints remain unchanged.

If compatibility cannot be guaranteed, explicitly explain why and propose a migration path instead of making breaking changes.

---

## Overall Goal

The final architecture should transform EPIK8S into a modular platform capable of provisioning an entire accelerator control system from an empty Kubernetes cluster while remaining fully compatible with all current installations and deployment workflows.
